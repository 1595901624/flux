> 审计日期：2026-09-12
> 审计基线：`main_v2`，HEAD `f397823`，并包含审计时工作树中的未提交国际化/托盘修正

## 1. 结论摘要

### 2026-09-12 第一批修复进度

- P0-01：已完成代码侧封堵——服务只启动安装器复制到 Program Files 的固定内核、安装时生成 SHA-256 清单并在每次启动校验、按客户端 SID 隔离、校验 ConfigDir、拒绝重解析点、使用 ArgumentList、限制非所有者停止。仍需真实双用户 ACL/TOCTOU 攻击测试后关闭。
- P0-02：标准安装的 `%APPDATA%` 身份错位已通过客户端 SID 推导修复；portable 路径由命名管道客户端真实进程目录和 `.config/PORTABLE` 标记共同推导，不再信任请求声明。仍需真实 portable TUN 测试。
- P0-03：三 RID 服务/安装器发布编排已加入，x86/x64/ARM64 本地 publish 均产生正确架构载荷；仍需 GitHub Actions/MSIX 实跑后关闭。
- P1-01：已加入 Sidecar/Service 显式迁移、服务失败禁止非特权回退，并统一首页/设置/热键权限与回滚；仍需真实 TUN 集成测试。
- P1-02：Service 模式已增加真实状态监控；核心退出或连续失联会停止流并撤销系统代理。仍需服务崩溃/重启与退避策略集成测试。
- P1-03/P1-04：恢复后会重载内存配置；文件事务增加失败逆序回滚；恢复前自动创建安全备份，恢复后核心启动失败会恢复原配置和原运行状态。仍需磁盘/文件占用故障注入测试。
- P1-09：自动更新定时器已遵守 AllowAutoUpdate。
- P1-10：MainWindow 关闭时停止 timer、退订流量事件并释放 EndSessionHook。
- P2-01/P2-02/P2-04：已修复速度排序、显示/隐藏热键、WebDAV 嵌套目录与非 localhost 明文 HTTP Basic。

当前项目不能认定为“已经按规划实现所有功能”。更准确的状态是：主程序基础流程、部分核心契约和一批页面骨架已经完成；但 Windows Service/TUN 的发行与权限模型尚未闭环，多项规划功能只存在于接口、数据模型或单元测试中，没有生产调用路径，也有若干已经接入但行为错误的功能。

审计时最新工作树的自动化结果：

- `dotnet build Flux.slnx -c Release --no-restore -warnaserror`：通过，0 警告、0 错误。
- `dotnet test Flux.slnx -c Release --no-build`：157/157 通过。
- `python scripts/check_uid_props.py`：0 个 x:Uid 属性错误。
- `python scripts/scan_i18n_gaps.py`：仍报告 Settings 页面 2 处真实可见硬编码；语言名称、默认配置注释和代理组识别关键词属于可接受例外。
- 测试主要覆盖纯函数、解析器、协议帧和配置构建器；没有真实 Windows Service、SCM/UAC、命名管道身份、TUN 模式切换、打包产物、WinUI 页面流程和崩溃恢复集成测试。因此“157 个测试全过”不能证明产品功能闭环。

## 2. 优先级定义

| 级别 | 定义 | 处理要求 |
|---|---|---|
| P0 | 安全边界失效、核心卖点不可交付、正式产物缺关键组件 | 立即停止发布，串行修复并做专项复审 |
| P1 | 主流程错误、数据一致性风险、已承诺功能不可用或大量缺失 | P0 后立即修复，功能对齐前必须清零 |
| P2 | 明显行为错误、局部功能残缺、长期运行问题 | P1 后按模块并行处理 |
| P3 | 国际化、工程卫生、体验和可维护性问题 | 稳定化阶段处理，但纳入发布门禁 |

## 3. P0：发布与安全阻断项

### P0-01 特权服务可执行不可信的 mihomo，并且 `ConfigDir` 未校验

证据：

- `Flux.Core/Service/ServicePathValidator.cs:38-50` 只做规范化字符串前缀和文件名判断；没有校验文件签名、发布清单哈希、文件所有者/ACL、重解析点或最终解析路径。
- 允许的内核目录包含应用安装目录下的 `core`。当前发行方式包含 portable ZIP，应用目录通常归普通用户可写；安装服务后，用户可替换 `core/mihomo.exe`，再要求 LocalSystem 服务启动它。
- `Flux.Service/RequestHandler.cs:45-59` 校验 `ConfigPath` 和 `CorePath`，但不校验 `request.ConfigDir`。
- `Flux.Service/PrivilegedCoreManager.cs:31-46` 直接把 `ConfigDir` 用作 SYSTEM 进程工作目录和 mihomo 的 `-d` 参数。
- `Flux.Service/PipeServer.cs:74-81` 向 `InteractiveSid` 授予读写权限，即所有交互式登录用户都可调用服务，而非安装服务的特定用户。

影响：一旦服务真正随包分发并被安装，portable/用户可写目录场景存在本地提权面；任意交互用户还可能借未验证的 `ConfigDir` 让 SYSTEM mihomo 在非预期位置读取或写入数据。简单的 `StartsWith` 也无法阻止 junction/symlink/reparse-point 绕过。

修复要求：

1. 服务只能启动服务自己管理、位于管理员可写目录中的已验证内核；禁止从普通用户可写的 portable 目录直接执行。
2. 更新内核时使用“下载到临时文件 → 哈希/签名验证 → 管理员侧原子替换”，并保存可信清单。
3. 对 `ConfigPath`、`CorePath`、`ConfigDir` 统一做最终路径解析、重解析点策略、存在性、文件类型、ACL/所有者检查。
4. 管道按安装用户 SID 或经身份认证的会话授权，不使用全局 `InteractiveSid`；服务端记录并校验客户端身份。
5. 请求参数使用结构化 `ArgumentList`，不要拼接 `Arguments` 字符串。
6. 增加普通用户替换内核、junction 绕过、伪造 `ConfigDir`、第二用户调用管道的负向集成测试。

验收：上述攻击路径全部被拒绝，服务事件日志含调用 SID、请求 ID 和拒绝原因；安全复审通过后才能恢复服务发行。

### P0-02 服务与 UI 对数据目录的解析身份不同，普通用户服务模式会拒绝配置

证据：

- UI 在 `Services/Paths.cs:46-55` 按当前交互用户解析 `%APPDATA%\flux`。
- 服务在 `Flux.Service/FluxServiceWorker.cs:20-21` 以自身进程身份调用 `ResolveDataDir`。
- `Flux.Core/Service/ServicePathValidator.cs:55-61` 也使用 `%APPDATA%\flux`；Windows Service 以 LocalSystem 运行时，它指向 systemprofile，而不是 UI 用户目录。
- UI 在 `Services/CoreProcessService.cs:57-58` 发送交互用户的 `runtime.yaml` 和数据目录；服务在 `Flux.Service/RequestHandler.cs:45` 用 systemprofile 数据目录校验该路径。

影响：非 portable 的普通用户场景下，即使服务安装成功，`start_core` 也会因配置路径不在服务认为的数据目录内而失败。该问题直接破坏“普通用户无需管理员启动即可启用 TUN”的核心验收目标。

修复要求：明确多用户模型。推荐由服务为每个经认证的用户 SID 派生其数据目录，或由 UI 把配置复制到服务私有目录并让服务验证/管理；不要依赖 LocalSystem 的 `%APPDATA%`。协议中增加用户身份/会话与服务端推导出的允许根目录，不能信任客户端自行声明根目录。

验收：标准安装、portable、两个 Windows 用户、服务重启四种场景下，普通用户均能安全启动/停止 TUN，且用户之间无法访问或控制对方配置。

### P0-03 正式发行产物不包含服务和安装器，且辅助项目仅支持 x64

证据：

- `.github/workflows/build-msix.yml:51-55` 仅 `dotnet publish Flux.csproj`。
- `Flux.csproj:49-62` 只引用 `Flux.Core`，并把 Service/Installer 从主项目 glob 中移除；没有复制其发布产物的 target/content。
- `Services/PrivilegeBroker.cs:110-114` 运行时要求主程序目录存在 `Flux.Service.Installer.exe`，缺失即失败。
- `Flux.Service.Installer/Program.cs:41-46` 又要求安装器同目录存在 `Flux.Service.exe`。
- `Flux.Service/Flux.Service.csproj:13` 与 `Flux.Service.Installer/Flux.Service.Installer.csproj:13` 均锁死 `x64`，而主程序发布 `win-x86/win-x64/win-arm64`。
- 当前普通 `dotnet build` 的三个项目输出位于不同目录；主程序输出目录中没有两个服务 EXE。

影响：CI 生成的 portable/MSIX 主程序无法安装服务；x86/ARM64 即使人工复制也无法形成架构一致的服务包。UI 中“安装服务”是不可交付入口。

修复要求：建立统一发行编排，按 RID 分别 self-contained publish 主程序、服务和安装器；复制到明确布局；为每个架构验证 PE 架构和文件存在性；MSIX/portable 分别定义服务安装策略；安装器、服务、应用共享版本源。

验收：CI 对每个 RID 解包后执行产物清单测试；在干净的 x64、ARM64（及仍承诺支持时的 x86）Windows VM 上完成安装、UAC、启动、修复、卸载和升级测试。

## 4. P1：主流程与数据一致性

### P1-01 TUN 模式切换没有完成 Sidecar/Service 状态迁移

证据：

- `Services/CoreProcessService.cs:54-72` 只在完整 `StartAsync` 时选择 Service，服务失败后还会无条件回退 Sidecar。
- `Services/CoreProcessService.cs:234-261` 的设置应用优先热重载；启用 TUN 时不会主动把已经运行的 Sidecar 迁移到 Service。
- `ViewModels/HomeViewModel.cs:316-322` 对所有非管理员直接拒绝 TUN，即使服务已就绪；Settings 页 `Views/SettingsPage.xaml.cs:293-309` 却允许服务就绪的普通用户，两个入口语义冲突。
- `Views/SettingsPage.xaml.cs:91` 仅在管理员进程中把 TUN 开关显示为开启，也忽略服务模式。
- 热键 `Services/AppBootstrapper.cs:175-178` 先持久化开关再 Apply，没有权限前置检查和失败回滚。

影响：同一功能从首页、设置、热键进入会得到不同结果；已运行 Sidecar 时开启 TUN 可能没有迁移到特权服务；服务启动失败后回退非特权 Sidecar 会制造“设置已开、实际不可用”的状态。

修复要求：把 TUN 切换做成单一事务状态机：预检能力 → 生成/校验配置 → 停旧模式 → 启新模式 → 控制器/TUN 设备健康检查 → 提交设置；任一步失败恢复旧进程与旧设置。所有 UI/热键/托盘只调用这一入口。TUN 请求不得静默回退 Sidecar。

验收：管理员 Sidecar、普通用户 Service、无服务、服务断开、启用失败、禁用恢复、应用重启七组端到端用例全部通过。

### P1-02 服务内核死亡后客户端仍报告运行，且没有崩溃退避/恢复

证据：

- `Services/CoreProcessService.cs:17-26` 的 Service `IsRunning` 只读本地布尔值 `_serviceCoreRunning`。
- `Flux.Service/PrivilegedCoreManager.cs:18-21` 能查询真实进程状态，但 UI 没有持续状态同步。
- `Flux.Service/PrivilegedCoreManager.cs:49-66` 未注册进程退出后的状态通知、错误传播或有限重启。

影响：服务内 mihomo 崩溃后首页、托盘和系统代理可能继续认为核心可用，导致用户断网；规划要求的崩溃检测、退避和诊断未实现。

修复要求：协议增加状态查询/事件或心跳；UI 以服务真实状态为准；异常退出立刻撤销系统代理或进入有限次数指数退避；将退出码、最近 stderr 和重启次数写入诊断。

### P1-03 备份恢复替换磁盘文件后没有重载内存配置

证据：

- `Flux.Core/Backup/LocalBackupService.cs:155-176` 直接替换 `config.yaml/verge.yaml/profiles.yaml` 和 profiles 文件。
- `Services/ConfigService.cs:26-32` 只在启动时加载一次，三个 Load 方法均为私有，没有公开 Reload/transaction API。
- 本地和 WebDAV 恢复在 `Views/SettingsPage.xaml.cs:629-631`、`:748-753` 替换文件后直接调用 `Core.RestartAsync()`，仍使用旧的 `AppServices.Config` 内存对象。

影响：界面提示“恢复成功”，但重启内核仍基于旧配置；之后任意保存可能把刚恢复的文件覆盖回旧值。用户会遇到恢复不生效或数据再次丢失。

修复要求：恢复必须由应用级协调器执行：停止写入/定时任务 → 校验完整备份 → 建立当前快照 → 原子替换 → 重新构造并校验 ConfigService/API/Streams → 重启核心 → 成功后提交；失败则完整回滚并恢复原进程。

### P1-04 所谓“原子恢复”没有异常回滚，可能留下半恢复状态

证据：`Flux.Core/Backup/LocalBackupService.cs:152-180` 把旧文件移到 rollback 目录后逐个移动新文件，但方法没有 catch 回滚逻辑；任何中途异常都会留下新旧文件混合，rollback 目录也只是记录在成功日志中。

影响：磁盘满、文件占用、权限或杀毒软件干预时，配置集合会变成不一致版本，可能导致下次启动失败。

修复要求：恢复前验证所有条目、schema、大小和 YAML；写入同文件系统 staging；用明确 commit/rollback 过程；故障注入测试覆盖每一步失败；启动时检测并恢复未完成事务。

### P1-05 配置体系出现“两套模型”，大量规划功能是未接线的死代码

证据：

- `Flux.Core/Settings/FluxSettings.cs` 与 `SettingsStore` 定义了完整 General/Proxy/Core/TUN/DNS/Tunnel/UI/Backup/Update 设置。
- 生产组合根 `Services/AppServices.cs:23-37` 仍只创建旧的 YAML `ConfigService`；全仓生产代码没有构造或调用 `SettingsStore`。
- `AppServices` 甚至把不存在于实际配置流的 `flux-settings.json` 加入备份清单。
- 实际 `Models/VergeConfig.cs` 只包含一小部分开关；规划中的启动页、托盘点击行为、代理守护间隔、代理主机/PAC 内容、独立 HTTP/SOCKS 端口、CORS、完整 TUN/DNS/Tunnel、Web UI、布局主题、通知位置、自动备份/日志清理/延迟测试和内核通道均未接入。

影响：接口和单元测试制造“已实现”假象，但用户无法配置，运行时也不会消费。两套 schema 后续会持续产生迁移、备份和默认值分叉。

修复要求：先做架构决策，只保留一个权威设置模型和存储；建立旧 YAML 到新 schema 的迁移；每个字段必须同时具备 UI/命令入口、持久化、运行时消费者、回滚和测试，不能以“模型存在”标记完成。

### P1-06 运行时构建器支持 DNS 覆写和链式代理，但生产输入永远不传入

证据：

- `Flux.Core/Config/RuntimeConfigBuilder.cs:82-94` 有 `EnableDnsSettings/DnsOverride/ChainProxy` 分支。
- `Services/ConfigService.cs:326-335` 构造 `RuntimeConfigInput` 时只传 Profile、ClashBase、ChainItems、EnableTun 和 EnableBuiltinEnhance。
- 生产 UI/服务没有 `ChainProxy` 调用路径。

影响：对应单元测试通过不代表功能存在；DNS 专用覆写和临时链式代理均未实现为产品功能。

修复要求：在统一设置模型后接线；链式代理需要入口/出口选择、循环检测、事务应用和退出清理；DNS 覆写需要完整模型、YAML 往返、mihomo `-t` 校验与回滚。

### P1-07 配置编辑、可视化编辑和 URI 导入未达到规划要求

证据：

- `Flux.Core/Proxies/ProxyUriParser.cs` 支持多种协议，但全仓生产代码没有调用，只有测试引用。
- `Views/EnhanceEditorDialog.cs:19-83` 只是普通 TextBox；没有规划要求的离线 WebView2 + Monaco，也没有可视化规则/节点/组编辑。
- `Views/EnhanceEditorDialog.cs:132-135` 的“脚本校验”只是检查文本是否包含字符串 `main`，并非语法/签名校验；真正沙箱错误只能到应用配置阶段发现。
- Profiles 菜单只有“编辑信息/编辑增强”，没有本地 YAML 正文编辑；`Services/SubscriptionService.cs:151-163` 创建的空配置只有注释，因此用户通过 UI 创建后无法把它编辑成可用配置。

影响：规划中的核心配置工作流没有完成；空配置、URI 批量导入、可视化编辑均不可用或不可达。

修复要求：建立一个共享 AST/DTO，原始 YAML 与可视化编辑共用；接入 URI 批量解析、逐项错误提示和去重；本地配置必须可编辑；保存前实际运行脚本编译/沙箱预演和 mihomo 校验。

### P1-08 应用更新、内核更新和 GeoData 更新只有接口或检查页

证据：

- `Flux.Core/Contracts/ServiceContracts.cs:132-135` 的 `CheckCoreUpdateAsync/DownloadCoreAsync` 没有实现类和生产调用。
- `Flux.Core/Contracts/CoreContracts.cs:72` 的 `UpdateGeoDataAsync` 没有实现；`MihomoApiService.UpdateGeoAsync` 也没有 UI 调用。
- `Views/SettingsPage.xaml.cs:784-824` 只查询 GitHub release 并打开浏览器，没有下载、校验、替换、回滚或 MSIX AppInstaller 流程。

影响：规划阶段 5/7 中的稳定/预览内核切换、缓存版本、GeoData 原子更新和应用自更新均未完成。

修复要求：分别定义 portable 与 MSIX 更新状态机；所有二进制更新必须校验架构、哈希/签名并可回滚；核心更新必须与 P0 服务信任模型共用同一可信仓库和清单。

### P1-09 订阅“允许自动更新”开关被定时器忽略

证据：`Models/ProfilesConfig.cs` 有 `AllowAutoUpdate`，但 `Services/SubscriptionService.cs:490-493` 只检查类型和间隔，没有检查该开关。

影响：用户明确关闭自动更新后，订阅仍会被后台替换，属于设置承诺违背和配置数据风险。

修复要求：统一使用 `ProfileItem.NextUpdateTime` 或集中 eligibility 判断；定时器启动幂等；加入关闭开关、间隔、304、失败保留旧文件和并发更新测试。

### P1-10 轻量模式没有释放 MainWindow，反而累积窗口和计时器

证据：

- `Services/LightweightManager.cs:22-36` 宣称关闭并释放主窗口。
- `MainWindow.xaml.cs:71-83` 用匿名 lambda 订阅单例 `AppServices.Streams.Traffic`，并启动 DispatcherQueueTimer。
- `MainWindow.xaml.cs:57` 关闭时只清空静态引用，没有退订 Traffic、停止 timer 或释放 `_endSessionHook`。

影响：Streams 持有旧窗口闭包，使窗口无法 GC；每次进入/退出轻量模式都会增加一个订阅和 timer，出现重复刷新、内存增长和句柄泄漏，违背轻量模式目的。

修复要求：MainWindow 实现确定性 Dispose/Closed 清理，事件使用可退订的命名处理器；停止 timer、退订 stream、释放 EndSessionHook；增加 20 次轻量模式往返的内存/订阅计数测试。

## 5. P2：明显行为错误与局部残缺

### P2-01 连接排序把瞬时速度和累计流量相加

`ViewModels/ConnectionsViewModel.cs:203-210` 使用 `UploadSpeed + Item.Upload`、`DownloadSpeed + Item.Download` 排序。量纲不同，长连接累计字节会永久压过当前高速连接；切回 default 时方法直接返回，也不能恢复初始/时间顺序。

修复：上传/下载分别只按速度排序；保存稳定次序键（如首次出现序号或开始时间）；默认排序显式重排；加动态快照测试。

### P2-02 “显示/隐藏窗口”热键只会显示

`Services/AppBootstrapper.cs:180-182` 无条件调用 `App.ShowMainWindow()`，窗口可见时不会隐藏；UI 文案却承诺显示/隐藏。

修复：维护真实可见/最小化状态并切换；隐藏时启动轻量倒计时；恢复时前置激活窗口。

### P2-03 热键能力只暴露 4 项，契约中的模式和轻量模式不可配置

`Flux.Core/Contracts/ServiceContracts.cs:141-148` 定义规则/全局/直连、系统代理、TUN、显示隐藏、重新激活、轻量模式；`Views/SettingsPage.xaml:142-155` 只提供显示隐藏、系统代理、TUN、重新激活四项。

修复：由动作注册表同时生成设置 UI、校验和执行映射，避免契约与页面再次分叉。

### P2-04 WebDAV 嵌套目录创建错误，并允许 Basic 凭据走明文 HTTP

- `Flux.Core/Backup/WebDavClient.cs:37-46` 循环每段时把 `partial` 重置为当前 segment；`a/b` 实际创建 `a` 和 `b`，而不是 `a/b`。
- `Flux.Core/Backup/WebDavClient.cs:15-29` 接受 `http` 并发送 Basic Authorization，非 TLS 时凭据可被截获。
- 每次页面操作创建一个持有 HttpClient 的 WebDavClient，类未实现 IDisposable，也未复用客户端。

修复：累计路径并逐级 MKCOL；默认强制 HTTPS，仅对 localhost 明确例外；使用 HttpClientFactory/共享客户端；限制下载大小并验证 ZIP 后再落盘。

### P2-05 代理页仍缺规划中的完整交互

当前 `Views/ProxiesPage.xaml` 和 `ViewModels/ProxiesViewModel.cs` 只有模式、Provider、文本筛选、分组卡片和测速；缺少排序、复杂筛选、每组测速 URL、紧凑/详细布局切换、组导航和链式代理入口。

修复：按独立故事拆分，每项写 ViewModel 单测和 WinUI 流程测试；不要仅增加 DTO 或解析器。

### P2-06 设置页只覆盖规划字段的子集

当前 Settings 页没有独立 HTTP/SOCKS 端口、PAC 内容/host、代理守护间隔、控制器 CORS/private-network、完整 TUN 字段、完整 DNS、Tunnel 编辑、启动页/脚本、托盘点击行为、Web UI、代理布局/图标、通知位置、自动备份/日志清理等入口。

修复：先完成 P1-05 单一设置模型，再按“字段 → UI → 验证 → 持久化 → 运行时消费 → 回滚 → 测试”闭环逐项实现。

## 6. P3：质量与工程卫生

### P3-01 国际化仍有真实可见硬编码

`Views/SettingsPage.xaml:180` 的“诊断与更新”和 `:192` 的 GitHub 标题/描述没有 x:Uid。语言列表使用语言自身名称应作为扫描器白名单；`HomeViewModel` 的中文代理组关键词和空配置注释不是直接 UI 文本，也应通过精确规则排除，避免扫描噪音。

### P3-02 仓库跟踪 Python 字节码并存在行尾噪音

`scripts/__pycache__/*.pyc` 被 Git 跟踪，当前还有一个二进制文件被修改；大量文件提示 LF 将转 CRLF。应移除已跟踪字节码、补 `.gitignore`，并用 `.gitattributes` 固定文本行尾，减少无意义 diff。

### P3-03 版本源分叉

主程序版本为 0.3.0，Service/Installer 为 0.1.0；当前只校验协议版本，`ServiceInstallState.VersionMismatch` 没有实际产品判断路径。应由 Directory.Build.props 或构建参数提供统一版本，并明确“协议不兼容”和“二进制版本过旧”两种状态。

### P3-04 缺少发行级端到端测试门禁

现有测试文件没有 UI 自动化、SCM/UAC、真实管道 ACL、多用户、TUN、portable/MSIX 产物和升级恢复测试。应建立 Windows VM 测试矩阵；仅跑 `dotnet test` 不得作为“全功能完成”的依据。

## 7. 推荐修复顺序与依赖

### 波次 A：安全冻结（必须串行）

1. P0-01：冻结服务协议与信任边界，先写威胁模型和负向测试。
2. P0-02：确定服务多用户数据目录模型。
3. P0-03：在安全模型确定后重做发行编排；此时才允许把服务放入产物。

退出条件：安全测试通过，portable 与 MSIX 的服务策略已书面确定；未经验证的用户可写 EXE 不可能被 SYSTEM 启动。

### 波次 B：核心生命周期

1. P1-01：实现统一 TUN/运行模式状态机。
2. P1-02：实现服务真实状态、崩溃检测和安全撤销代理。
3. 补 Windows VM 的 TUN、服务重启、版本不匹配和异常退出测试。

退出条件：普通用户服务模式是唯一事实来源，任何入口行为一致，失败不会留下 TUN/系统代理脏状态。

### 波次 C：配置与数据一致性

1. P1-05：合并两套设置体系，这是后续功能的前置依赖。
2. P1-03/P1-04：把备份恢复纳入应用级事务并支持重载。
3. P1-06/P1-07：接线 DNS、链式代理、正文/可视化编辑、URI 导入。
4. P1-09：修正订阅自动更新 eligibility。

退出条件：所有设置只有一个权威来源；备份恢复可在故障注入下回滚；每个“已实现”功能都有真实用户入口和运行时消费者。

### 波次 D：更新与发行能力

1. P1-08：应用、内核、GeoData 更新。
2. 与 P0 的签名/哈希/服务私有内核仓库合并实现。
3. 验证从旧版本升级、更新失败回滚、架构匹配和服务同步升级。

### 波次 E：页面补齐与稳定性

1. P1-10 轻量模式泄漏。
2. P2-01 至 P2-06 页面行为与缺失功能。
3. P3 国际化、版本、仓库卫生和 CI 门禁。

## 8. Agent 拆分建议

为避免再次出现“模型/接口已写但功能未接线”，每个 agent 的任务必须以可验证纵向切片为单位，并禁止多个 agent 同时修改同一权威配置模型。

| Agent | 任务边界 | 前置依赖 | 强制交付物 |
|---|---|---|---|
| Security-Service | P0-01/P0-02 | 无 | 威胁模型、协议、ACL/身份、路径与二进制验证、负向测试 |
| Packaging | P0-03/P3-03 | Security-Service 定稿 | 三 RID 产物、清单校验、版本统一、VM 安装脚本 |
| Core-Lifecycle | P1-01/P1-02 | 新服务协议 | TUN 状态机、健康同步、崩溃恢复、端到端测试 |
| Settings-Migration | P1-05 | 无，但需独占配置模型 | 唯一 schema、迁移、备份字段定义、兼容测试 |
| Backup | P1-03/P1-04/P2-04 | Settings-Migration | 事务恢复、重载、WebDAV 修正、故障注入测试 |
| Profile-Editor | P1-06/P1-07/P1-09 | Settings-Migration | 编辑器、URI 导入、DNS/链式代理接线、订阅测试 |
| Updater | P1-08 | Security-Service + Packaging | App/Core/Geo 更新状态机、校验与回滚 |
| UI-Stability | P1-10、P2、P3-01 | Core/Settings 接口稳定 | 页面行为、轻量模式、国际化、UI 自动化 |

每个任务的完成定义：

1. 用户入口可达，不接受“只有接口/模型/解析器”。
2. 成功路径、失败路径、取消路径和重启恢复均有测试。
3. 所有持久化变更有验证和回滚。
4. `build -warnaserror`、单元测试、产物清单测试、对应 Windows VM 集成测试全部通过。
5. 在功能矩阵中附代码入口、运行时消费者和测试名，再标记 Implemented。

## 9. 最终发布门禁

发布候选必须同时满足：

- P0/P1 为 0；P2 若延期必须有明确范围说明且不冒充完整对齐。
- 三架构产物与承诺一致；若停止支持 x86，应同步删除 RID、文档和工作流，而不是生成残缺包。
- 普通用户 TUN、服务升级/修复/卸载、系统代理异常退出恢复通过干净 VM 实测。
- 备份恢复后内存状态、磁盘状态、运行核心一致，且中途失败可自动回滚。
- 所有规划功能在矩阵中有真实入口、持久化位置、运行时消费者和测试证据。
- portable 与 MSIX 更新、签名、哈希、回滚策略均通过验证。
- WinUI 关键流程至少覆盖首次启动、导入/编辑订阅、节点切换、系统代理、TUN、增强保存失败、备份恢复、更新失败、轻量模式往返和退出。
